このブログはHugoで作っていて、手元のノートPCで `hugo --minify` を叩くと、毎回1分半ほど待たされる。Hugoは「1ページあたり1ミリ秒未満」でサイトを組み立てられることを売りにしている静的サイトジェネレーターで、この数字をそのまま当てはめれば、2,000ページ強のサイトは2〜3秒で終わるはずだ。手元ではその30倍以上かかっていることになる。

テンプレートの書き方が悪いのか、画像が多すぎるのか、それとも別のところに原因があるのか。勘で設定をいじる前に、ビルドの中身を一つずつ外しながら時間を測り、どこで時間が消えているかを切り分けておくことにした。使ったのはHugo v0.166.0 extended(Windows版)、Windows 11、Core i5-1235U、メモリ16GBのノートPCだ。比較用に、同じHugoのバージョンで動いているGitHub Actionsのビルドログも並べている。

## 計測の前提、2,189ページの内訳

HugoはGo言語で書かれた静的サイトジェネレーターで、2013年にSteve Franciaが公開し、2015年ごろからはBjørn Erik Pedersenが開発の中心を担っている。Markdownの原稿とテンプレートを読み、HTMLのファイル群を書き出すまでを1つの実行ファイルでこなす。外部のランタイムを入れなくていいので、Windowsのノートでもサーバーでも同じ手順で動かせるのが気に入っている。

ビルドが終わると、Hugoは作ったものの内訳を表で出してくれる。このブログの場合は次のとおりだった。

| 項目 | 件数 |
|---|---|
| Pages(HTMLを持つページ) | 2,189 |
| Paginator pages(一覧の2ページ目以降) | 56 |
| Static files(画像などのコピー) | 1,158 |
| Processed images(Hugoが加工した画像) | 0 |
| Aliases(転送用のページ) | 1,035 |

記事の本数は247本しかないのに、ページは2,189もある。差の大部分はタグのページで、記事に付けたタグは全部で933種類あった。タグ1つにつき一覧ページが1枚でき、さらにそのタグのRSSと、一覧の1ページ目を指す転送用のページ(`/page/1/` から本来のURLへ飛ばすもの)が作られる。記事1本に対して、書き出されるファイルは10本を優に超えている計算になる。

一方で、加工した画像は0枚だった。写真はすべて縮小済みのものを `static/` に置いているので、Hugoの画像処理は一度も動いていない。ビルドが遅いサイトでよく疑われるのは画像のリサイズだが、少なくともこのブログでは、その線は最初から消えていることになる。

## 5回ビルドして、ばらつきを見る

<figure class="photo photo--right">
<a href="https://gohugo.io/" target="_blank" rel="noopener"><img src="/images/hugo-build/stopwatch.jpg" alt="白い文字盤に黒と赤の目盛りが入った、銀色の機械式ストップウォッチ" width="220" height="235" loading="lazy"></a>
<figcaption>計測は1回では信用しない。出力先を空にして同じビルドを5回繰り返した<span class="credit">Photo: Al Riaz Uddin / <a href="https://commons.wikimedia.org/wiki/File:Analog_stopwatch.jpg" target="_blank" rel="noopener">CC BY-SA 4.0</a></span></figcaption>
</figure>

まず、普段どおりのビルドを繰り返して基準を作った。出力先は作業用の一時フォルダにして、毎回フォルダを消してから `hugo --minify -d <出力先>` を実行し、Hugo自身が最後に表示する「Total in ◯ms」を記録している。結果は92.3秒、99.3秒、98.8秒、96.7秒、96.4秒で、平均すると約96.7秒になった。7秒ほどの幅があるので、以降の比較では数秒の差は誤差として扱う。

出力先を消さずに上書きした場合も2回測った。こちらは76.0秒と92.3秒で、1回目は少し速く出たものの、2回目はほとんど変わらなかった。Hugoは既存のファイルを残したまま書き直すので、書き込む量そのものは減らない。上書きで劇的に速くなることはない、と考えてよさそうだ。

もう一つ、`--minify` を外したビルドも測った。HTMLから空白や改行を削る処理を丸ごと省いたのに、結果は97.1秒で、平均と見分けがつかない。圧縮の処理は、この規模では時間の勘定にほとんど入っていないことになる。

## テンプレートの計測では25秒ぶんしか見えない

次に疑ったのはテンプレートだ。Hugoには `--templateMetrics` という計測用のオプションがあり、`--templateMetricsHints` を添えると、テンプレートごとの実行時間と「キャッシュできる余地」を一覧にしてくれる。上位はこうなった。

| テンプレート | 累積時間 | 平均 | 呼び出し回数 | キャッシュ余地 |
|---|---|---|---|---|
| list.html | 7.56秒 | 7.41ms | 1,020 | 0% |
| single.html | 3.99秒 | 15.95ms | 250 | 0% |
| _partials/head.html | 3.96秒 | 3.10ms | 1,275 | 56% |
| _partials/header.html | 2.36秒 | 1.85ms | 1,275 | 99% |
| rss.xml | 1.36秒 | 1.41ms | 967 | 0% |
| alias.html | 1.04秒 | 1.00ms | 1,035 | 0% |

一覧ページを作る `list.html` が1,020回呼ばれて最も時間を食っている。これはほぼタグのページだ。記事本体の `single.html` は1回あたり16ms近くかかるものの、回数が250回なので合計では2番手になる。キャッシュ余地が99%と出た `header.html` は、どのページでもほぼ同じ中身を作っているという意味で、`partialCached` に置き換える候補になる。同じテーマの `footer.html` はすでにキャッシュされていて、1,275回のうち1,267回が使い回しだった。

ただ、表の累積時間をすべて足しても25秒ほどにしかならない。しかもこれは各処理の時間を単純に積み上げた値で、Hugoはページを12スレッドで並行して描くので、実際の待ち時間に占める割合はさらに小さい。全体が95秒なのに、テンプレートで説明できるのはせいぜい数秒ということになる。header を `partialCached` に変えれば計測表の数字は減るが、体感できるほど待ち時間が縮むとは思えなかった。

## メモリに描画すると1.3秒

<figure class="photo photo--left">
<a href="https://www.amazon.co.jp/s?k=NVMe+SSD+M.2&tag=nakimoto1-22" target="_blank" rel="noopener sponsored nofollow"><img src="/images/hugo-build/nvme-ssd.jpg" alt="黒い基板にNVMe SSD 960 EVOと書かれたラベルが貼られた、M.2形状のSSDの接写" width="220" height="124" loading="lazy"></a>
<figcaption>M.2形状のNVMe SSD。書き込みの速さは十分でも、小さなファイルを数千本作る処理では別の待ち時間が効いてくる<span class="credit">Photo: Daniel Aleksandersen / <a href="https://commons.wikimedia.org/wiki/File:Samsung_960_EVO_NVME_M.2_SSD_by_Daniel_Aleksandersen.jpg" target="_blank" rel="noopener">CC BY-SA 2.0</a></span></figcaption>
</figure>

テンプレートでないなら、残るのは原稿の読み込みか、ファイルの書き出しだ。これを切り分けるのに使ったのが `--renderToMemory` というオプションで、ページをすべて描いたうえで、結果をディスクに書かずにメモリの中に置いておく。開発用サーバー(`hugo server`)が普段やっているのと同じ動きだ。

同じ条件でこれを付けてビルドすると、Totalは1,302ミリ秒、つまり1.3秒で終わった。2,189ページを読み込み、テンプレートを通して描き上げるところまでは1.3秒で済んでいて、残りの94秒近くはディスクへの書き出しに使われていたことになる。比率にすると、待ち時間の98%以上がファイルの書き込みだった。

この見立ては、GitHub Actionsのログでも裏が取れた。同じv0.166.0がLinuxのランナーで2,186ページを組み立てたときのTotalは2,640ミリ秒で、ディスクに書き出したうえで3秒を切っている。Hugoが遅いのではなく、このノートPCでのファイルの書き込みが遅い。1ページ1ミリ秒未満という触れ込みは、Linuxの環境ではほぼそのとおりに出ている。

## 生成物を減らして比べる

書き込みが原因なら、書き出すファイルを減らせば時間は縮むはずだ。Hugoは設定項目を環境変数で上書きできるので、設定ファイルには手を付けずに、静的ファイルの置き場所を空のフォルダに向ける(`HUGO_STATICDIR`)のと、タグとカテゴリーのページを作らない(`HUGO_DISABLEKINDS="taxonomy term"`)のとを組み合わせて測った。

| 条件 | 書き出したファイル | Total |
|---|---|---|
| 普段どおり | 約4,400本 | 95.2秒 |
| 静的ファイルなし | 3,282本 | 73.2秒 |
| タグ・カテゴリーなし | 約1,520本 | 17.4秒 |
| 両方なし | 360本 | 0.78〜0.84秒 |
| メモリに描画(参考) | 0本 | 1.3秒 |
| GitHub Actions(参考) | 約4,400本 | 2.6秒 |

静的ファイル1,158本(合計125MB)を外すと22秒縮んだ。1本あたりおよそ19ミリ秒で、画像のコピーにも書き込みの待ちがしっかり乗っている。タグとカテゴリーのページを外したときの縮み方はそれ以上で、95秒から17秒まで落ちた。両方を外すと書き出すのは360本だけになり、ビルドは1秒を切った。

ページを作らない条件では描画の量も減っているので、この差がすべて書き込みの分だとは言い切れない。ただ、メモリに描画した場合の1.3秒が「全部描いた場合」の上限なので、描画の節約分はせいぜい1秒前後だ。残りの70秒あまりは、タグのページとそのRSSと転送ページ、合わせて3,000本近いファイルを書き出す時間だったと読める。

## タグ933個が作っていたもの

そこで、タグの付き方を数えてみた。933種類のうち、1本の記事にしか使われていないタグが775個あり、全体の約8割を占めていた。2本で使われているものが92個、5本以上の記事にまたがっているものは29個しかない。ほとんどのタグは、記事1本だけが載った一覧ページと、記事1本だけのRSSと、そこへ飛ばす転送ページの3本を作るためだけに存在していたことになる。

読む側から見ても、記事が1本しか載っていないタグの一覧は、その記事に戻ってくる以外の役に立たない。検索エンジン向けにはすでにタグのページを `noindex` にしているので、評価の面でも得るものがない。ビルド時間を食う一方で、サイトの回遊にもほとんど貢献していないわけだ。

手を入れる候補は3つ考えられる。1つ目はタグのRSSをやめることで、`[outputs]` の設定で `term = ["html"]` と書けば、タグごとのRSSは作られなくなる。これだけで900本以上のファイルが消える。2つ目はタグそのものを整理し、複数の記事にまたがる言葉だけを残すことだ。3つ目は転送ページで、Hugoには転送ページの生成を止める設定もあるが、このブログには記事のURLを変えたときに `aliases` で旧URLを残している記事が67本あるので、一律に止めるとそちらまで消えてしまう。今回は計測までにとどめて、設定はまだ変えていない。

## 次に試すことと、手元の環境の話

もう一つ気になっているのが、Windowsのリアルタイム保護だ。手元の設定を確認すると有効になっていて、新しいファイルが作られるたびに中身の検査が走る。数千本の小さなファイルを一気に書くビルドとは相性が悪いはずで、同じHugoがLinuxでは3秒を切ることを考えると、待ち時間の多くはここに吸われている可能性が高い。ただ、保護の対象から出力フォルダを外すのはセキュリティ上の判断になるので、今回は試していない。

実際の運用で一番効くのは、手元でのビルドの回数そのものを減らすことだと思う。

- 記事の見た目の確認は `hugo server` で行う。標準でメモリに描画するので、変更の反映は1〜2秒で終わる
- `hugo --minify` で公開用のファイルを書き出すのは、本当に `public/` の中身を確かめたいときだけにする
- 公開用のビルドはGitHub Actionsに任せる。同じ版で2〜3秒なので、手元より速く、結果も同じになる
- タグのRSSを止める変更を入れる前と後で、同じ手順で5回ずつ測り直す

なお、書き出し先のSSDが遅いわけではない。M.2のNVMe SSDは大きなファイルの連続書き込みなら毎秒数GBを出せるが、今回のように数KBのファイルを数千本作る処理では、ファイルを作るたびの手続きのほうが支配的になる。ディスクを速いものに替えるより、作るファイルを減らすほうが先だと感じた。とはいえ、写真や音源を大量に扱うPCでストレージの空きが少ないなら、そもそもの作業全体が窮屈になる。容量に余裕のあるNVMe SSDは[Amazonで容量と価格を見比べる](https://www.amazon.co.jp/s?k=NVMe+SSD+M.2&tag=nakimoto1-22)ことができる。

## まとめ

95秒かかっていたHugoのビルドを分解すると、ページを描くのに1.3秒、ファイルを書き出すのに残りの94秒近くを使っていた。テンプレートの計測で見える時間は全体のごく一部で、`partialCached` の候補を探す前に、`--renderToMemory` で描画と書き込みを分けて測るのが近道だった。

書き出すファイルの内訳を見ると、記事247本に対してタグ933個が3,000本近いファイルを作っていて、その8割は記事1本しか載らないタグだった。設定を変えずに環境変数で生成物を減らして比べるやり方は、ほかのHugoのサイトでもそのまま使える。次はタグのRSSを止め、同じ手順で測り直した結果をここに書き足すつもりだ。
